# AutoFolio

> 채용 사이트의 반복적인 지원서 입력 과정을 자동화하는 개인 취업 지원 도구

## 1. 프로젝트 개요

AutoFolio는 채용 지원 과정에서 반복적으로 입력해야 하는 정보를 자동으로 분석하고 채워 주는 도구다.

사용자가 매번 학력, 자격증, 어학, 수상, 경력 등의 정보를 직접 입력하는 대신, 미리 저장된 실제 이력 데이터를 기반으로 채용 사이트의 지원서 양식을 분석하고 적절한 정보를 선택하여 자동 입력한다.

단순 자동완성이 아니라 다음 과정을 목표로 한다.

**지원서 양식 분석 → 적절한 이력 선택 → 자동 입력 → 결과 검증 → 사용자 최종 확인**

최종 제출은 사용자가 직접 확인한 뒤 수행하는 것을 기본 원칙으로 한다.

---

## 2. 해결하려는 문제

채용 지원 시 회사마다 서로 다른 채용 사이트를 사용하지만 실제 입력하는 내용은 반복되는 경우가 많다.

예:

- 이름 및 연락처
- 주소
- 학력
- 전공
- 학점
- 자격증
- 어학 성적
- 수상 경력
- 프로젝트
- 활동 및 경험

문제는 사이트마다 다음 항목들이 다르다는 것이다.

- 필드 이름
- 입력 순서
- 입력 형식
- 선택 방식
- 날짜 형식
- 학력/자격증 검색 UI
- 필수 여부

따라서 단순히 고정된 CSS Selector를 저장하는 방식만으로는 여러 채용 사이트에 대응하기 어렵다.

AutoFolio는 페이지 구조와 필드 의미를 분석하여 사용자의 이력 데이터와 연결하는 것을 목표로 한다.

---

## 3. 핵심 목표

### 3.1 반복 입력 최소화

이미 입력한 개인 정보를 다른 채용 사이트에서 다시 입력하지 않도록 한다.

### 3.2 실제 이력 기반 입력

AI가 임의로 내용을 만들어내는 것이 아니라 사용자가 등록한 실제 이력 중에서 적절한 항목을 선택한다.

### 3.3 다양한 채용 사이트 대응

특정 회사 하나를 위한 스크립트가 아니라 서로 다른 지원 페이지에서도 동작할 수 있는 구조를 지향한다.

### 3.4 사용자 검증

자동 입력 결과를 사용자가 확인한 뒤 제출한다.

자동 제출 자체는 핵심 목표가 아니다.

---

## 4. AutoFolio와 Folio의 구분

AutoFolio와 Folio는 관련될 수 있지만 서로 다른 프로젝트다.

### Folio

취업 지원 정보를 관리하는 서비스.

예:

- 채용 공고 관리
- 지원 현황 관리
- 자기소개서 관리
- 일정 관리
- 지원 기록 관리

### AutoFolio

실제 채용 사이트에서 지원서를 작성하는 과정을 자동화하는 도구.

예:

- 지원 페이지 분석
- 입력 필드 의미 파악
- 사용자 이력과 매칭
- 지원서 자동 입력
- 입력 결과 검증

관계는 다음과 같다.

```text
Folio
 └─ 지원 정보 / 사용자 이력
          ↓ 선택적 연동
AutoFolio
 └─ 실제 채용 사이트 자동 입력
```

AutoFolio는 Folio와 연동할 수 있지만 **Folio가 없어도 단독으로 사용할 수 있어야 한다.**

---

## 5. 기본 사용자 흐름

```text
채용 사이트 지원서 접속
        ↓
AutoFolio 실행
        ↓
현재 페이지의 입력 필드 분석
        ↓
각 필드의 의미 추론
        ↓
사용자 이력 데이터 검색
        ↓
적절한 값 선택
        ↓
지원서 자동 입력
        ↓
입력 결과 검증
        ↓
사용자 확인
        ↓
사용자가 직접 제출
```

## 6. 핵심 기능

### 6.1 사용자 이력 관리

자동 입력에 사용할 실제 정보를 저장한다.

예:

```text
Personal
- 이름
- 연락처
- 이메일
- 주소

Education
- 학교
- 전공
- 입학일
- 졸업일
- 학점

Certificates
- 자격증명
- 취득일
- 발급기관

Languages
- 시험 종류
- 점수
- 취득일

Awards
- 수상명
- 기관
- 날짜

Activities
- 활동명
- 기간
- 내용

Projects
- 프로젝트명
- 기간
- 기술
- 설명
```

---

### 6.2 지원서 양식 분석

현재 페이지의 입력 요소를 수집한다.

분석 대상 예:

- `input`
- `textarea`
- `select`
- radio button
- checkbox
- custom dropdown
- date picker
- autocomplete UI

필드 자체뿐 아니라 주변 정보도 함께 활용할 수 있다.

예:

- label
- placeholder
- section title
- 주변 텍스트
- DOM 구조
- name / id
- 이미 선택된 값

---

### 6.3 필드 의미 추론

사이트의 필드와 사용자 데이터를 연결한다.

예:

```text
"대학교명"
→ Education.school

"최종학교"
→ Education.school

"졸업(예정)일"
→ Education.graduationDate

"공인어학시험"
→ Languages
```

단순 문자열 매칭으로 해결 가능한 경우에는 AI를 사용하지 않는다.

---

### 6.4 이력 선택

같은 종류의 이력이 여러 개 있을 수 있다.

예:

```text
자격증
├─ 정보처리기사
├─ SQLD
└─ COS Pro C++ 1급
```

페이지가 특정 개수의 자격증만 요구하거나 특정 조건을 요구한다면 AutoFolio가 적절한 후보를 선택한다.

불확실한 경우 자동 결정하지 않고 사용자에게 선택을 요청한다.

---

### 6.5 자동 입력

분석된 매핑 결과를 실제 페이지에 적용한다.

예:

```text
Education.school
→ "숭실대학교"

Education.major
→ "소프트웨어학부"

Certificate.name
→ "정보처리기사"
```

텍스트 입력뿐 아니라 드롭다운, 검색형 입력 UI 등도 처리하는 것을 목표로 한다.

---

### 6.6 입력 결과 검증

자동 입력 후 실제 페이지 상태를 다시 확인한다.

검증 예:

- 값이 실제로 입력됐는가
- 예상한 필드에 들어갔는가
- 필수 항목이 남아 있는가
- 입력 후 validation error가 발생했는가
- dropdown에서 올바른 항목이 선택됐는가

---

## 7. AI 사용 원칙

모든 입력을 LLM에 맡기지 않는다.

기본 전략은 다음과 같다.

```text
규칙 기반 처리
    ↓ 실패
기존 매핑 / 캐시 검색
    ↓ 실패
AI 추론
```

AI는 주로 의미 판단이 필요한 부분에 사용한다.

예:

- 처음 보는 필드의 의미
- 사용자 데이터와 필드의 연결
- 여러 후보 중 적절한 항목 선택
- 복잡한 사이트 구조 해석

명확한 작업은 규칙 기반으로 처리한다.

---

## 8. 로컬 AI

가능하면 필드 분석 과정에서 작은 로컬 모델을 활용하는 방향을 고려한다.

검토했던 후보:

- Laya 계열
- 소형 Qwen 계열

최종 모델은 아직 확정하지 않았다.

### 경량화 방향

- 작은 모델 사용
- 양자화
- 필요한 순간에만 모델 실행
- 이미 분석한 결과 캐싱
- 가능한 작업은 규칙 기반 처리

예:

```text
"휴대전화" → phone
```

같이 명확한 매핑에 매번 LLM을 호출할 필요는 없다.

한번 분석된 사이트 또는 필드는 캐시에 저장하여 재사용할 수 있다.

---

## 9. 브라우저 자동화 방식

최종 방식은 아직 확정하지 않았다.

현재 후보는 크게 두 가지다.

### Chrome Extension

장점:

- 사용자가 실제 지원 중인 브라우저에서 바로 실행 가능
- 현재 페이지 DOM에 직접 접근하기 편함
- UX가 자연스러움

검토할 점:

- 복잡한 브라우저 권한
- 확장 프로그램 구조
- 사이트별 보안 정책

### Playwright 기반 로컬 앱

장점:

- 강력한 브라우저 자동화
- 테스트 및 자동 조작이 편함
- 복잡한 UI 처리 가능

검토할 점:

- 사용자가 실제 사용하는 브라우저 세션과의 연결
- 로그인 및 인증 처리
- 사용 경험

MVP를 구현한 뒤 실제 사용성을 기준으로 결정한다.

---

## 10. 데이터 처리 방향

가능하면 사용자의 취업 관련 개인정보는 로컬에서 관리한다.

특히 다음 정보가 포함될 수 있다.

- 이름
- 연락처
- 주소
- 학력
- 성적
- 자격증
- 활동 내역

따라서 불필요하게 외부 서버로 전송하지 않는 방향을 우선한다.

AI 모델 역시 로컬 모델을 검토하는 이유 중 하나다.

---

## 11. MVP

AutoFolio의 첫 번째 목표는 범용 취업 자동화 플랫폼을 만드는 것이 아니다.

### MVP 목표

**실제 채용 사이트 한 곳에서 AutoFolio를 사용하여 지원서 일부를 자동으로 작성한다.**

### MVP 지원 범위

우선 다음 항목부터 구현한다.

- [ ] 기본 인적사항
- [ ] 학력
- [ ] 자격증
- [ ] 필드 분석
- [ ] 사용자 데이터 매핑
- [ ] 자동 입력
- [ ] 입력 결과 검증
- [ ] 사용자 최종 확인

### MVP 성공 조건

실제 채용 사이트 하나에서 다음 과정이 동작한다.

```text
사이트 접속
→ AutoFolio 실행
→ 지원서 필드 분석
→ 저장된 사용자 정보 선택
→ 자동 입력
→ 입력 결과 확인
```

---

## 12. MVP에서 하지 않을 것

초기 버전에서는 다음 기능을 우선하지 않는다.

- 자기소개서 자동 생성
- 채용 공고 적합도 점수
- 채용 공고 추천
- 지원 현황 대시보드
- 여러 회사 동시 지원
- 완전 자동 제출
- 모든 채용 사이트 지원
- 복잡한 Folio 통합

이 기능들은 AutoFolio의 핵심인 **지원서 자동 입력**이 실제로 작동한 이후 검토한다.

---

## 13. 검증 및 안전장치

AutoFolio는 지원서라는 중요한 데이터를 다루기 때문에 자동화보다 정확성이 우선이다.

### 원칙

1. AI가 존재하지 않는 이력을 만들어내지 않는다.
2. 사용자 데이터에 없는 내용은 임의 입력하지 않는다.
3. 확신할 수 없는 매핑은 사용자에게 확인한다.
4. 입력 후 실제 DOM 값을 다시 확인한다.
5. 최종 제출은 기본적으로 사용자가 수행한다.

예:

```text
[AutoFolio]

"자격사항 1"에 어떤 정보를 입력할까요?

○ 정보처리기사
○ SQLD
○ COS Pro C++ 1급
○ 입력하지 않음
```

## 14. 장기적인 구조

```text
                ┌─────────────────────┐
                │     User Profile    │
                │ 실제 사용자 이력 데이터 │
                └──────────┬──────────┘
                           │
                           ▼
┌────────────────────────────────────────────┐
│                AutoFolio                   │
│                                            │
│  Page Analyzer                             │
│       ↓                                    │
│  Field Classifier                          │
│       ↓                                    │
│  Profile Matcher                           │
│       ↓                                    │
│  Form Filler                               │
│       ↓                                    │
│  Validator                                 │
│                                            │
└──────────────────────┬─────────────────────┘
                       │
                       ▼
               채용 사이트 지원서
```

AI는 `Field Classifier`와 `Profile Matcher`를 중심으로 활용하고, 나머지는 가능한 한 일반 프로그램 로직으로 처리한다.

## 15. 향후 확장

핵심 기능이 검증되면 다음 기능을 고려한다.

### 사이트 학습 / 캐시

한 번 분석한 사이트의 구조를 저장하여 다음 지원에서 재사용한다.

```text
사이트 A
"school_nm" → Education.school
"major_nm" → Education.major
```

### Folio 연동

Folio에 저장된 지원 정보 또는 사용자 이력을 선택적으로 불러온다.

### 지원서 분석

아직 작성되지 않은 필수 항목이나 오류가 있는 항목을 표시한다.

### 사용자 프로필 관리

여러 버전의 이력 또는 지원 목적에 따른 프로필을 관리한다.

예:

- System SW 지원용
- Embedded 지원용
- 일반 SW 지원용

단, 실제 이력을 변경하는 것이 아니라 어떤 경험을 우선적으로 사용할지를 관리한다.

## 16. 개발 원칙

### YAGNI

필요성이 검증되기 전에 범용 플랫폼을 만들지 않는다.

### 실제 사이트 우선

가상의 완벽한 아키텍처보다 실제 채용 사이트 하나에서 작동하는 것을 먼저 목표로 한다.

### Rule First, AI When Needed

명확한 문제는 일반 코드로 해결한다.

AI가 필요한 문제에만 AI를 사용한다.

### Human in the Loop

불확실하거나 중요한 판단은 사용자가 확인한다.

### Local First

가능하면 개인정보 처리와 AI 추론을 로컬에서 수행한다.

---

## 17. 현재 결정된 것

- AutoFolio는 **지원서 자동 입력 프로젝트**다.
- Folio와는 별개의 프로젝트다.
- Folio 연동은 선택 사항이다.
- AutoFolio 단독으로도 사용할 수 있어야 한다.
- 실제 사용자 이력 데이터를 기반으로 입력한다.
- 사이트의 지원서 구조를 분석한다.
- 입력 후 검증한다.
- 최종 제출은 사용자가 확인한다.
- AI는 필요한 부분에만 사용한다.
- 로컬 소형 모델을 검토한다.
- Chrome Extension과 Playwright를 구현 후보로 검토한다.
- 첫 MVP는 **실제 채용 사이트 한 곳**을 대상으로 한다.

---

## 18. 아직 결정하지 않은 것

- Chrome Extension vs Playwright
- 최종 로컬 모델
- 사용자 데이터 저장 형식
- UI 구조
- 사이트 분석 캐시 구조
- Folio 연동 API
- 배포 형태

이 항목들은 MVP 구현 과정에서 실제 필요성을 확인한 뒤 결정한다.
